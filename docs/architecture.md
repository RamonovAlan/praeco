# Architecture baseline

Date: 2026-10-12

Praeco will begin as one Python service containing the Telegram bot, a small HTTPS surface for OAuth callbacks and health checks, one persistent worker, and explicit domain workflows. SQLite is the default database for the single-owner MVP. Media is stored as original local files on persistent storage. Docker Compose will provide reproducible deployment; a standard reverse proxy may terminate TLS.

The main boundaries are `bot`, `workflows`, `storage`, `jobs`, `ai`, `publishing`, `preferences`, and `observability`. Provider-specific behavior belongs behind narrow adapters. The core workflow must not know LinkedIn or AI-provider implementation details.

Publishing is approval-first. Text and image approvals point to immutable versions. A final click creates an immutable publication snapshot and an idempotent publication attempt. Ambiguous external outcomes enter `PUBLISH_UNKNOWN` and are never retried automatically.

The optional LinkedIn worker remains disabled by default. An owner callback persists the exact approved text/image versions before the worker decrypts the active member token, verifies the immutable image checksum, and calls the official Images and Posts APIs once. Confirmed, definitively failed, and ambiguous outcomes commit before a durable Telegram result is queued. An in-flight process interruption becomes `PUBLISH_UNKNOWN` and is never reclaimed automatically.

The pure in-memory workflow aggregate is implemented in `src/praeco/workflow.py`. It enforces owner access, legal state transitions, current-version approvals, text-to-image version binding, exact preview snapshot matching, one publish start, and the `PUBLISH_UNKNOWN` stop state. SQLite persistence, durable jobs, Telegram parsing/dispatch, mock provider execution, durable delivery scheduling, official Telegram transport, and a bounded application lifecycle now wrap that aggregate. Real AI and publishing adapters remain disabled; the aggregate alone is not a working bot.

Parsed Telegram updates enter a transactional dispatcher. The update claim, draft transition, and job reservation commit together through one outer transaction and repository savepoints. Provider and Telegram network calls remain outside that transaction: the dispatcher only creates durable work, and a separate worker must persist provider results before delivery.

The provider worker leases one job, validates local input, marks the external-call boundary, and invokes an injected provider outside any database transaction. A successful result, measured usage, and Telegram outbox intent commit together. Post-boundary provider exceptions remain `RESULT_UNKNOWN`; expired provider leases recover only calls that never crossed that boundary.

The delivery worker separately leases an outbox row that references one exact immutable text or image version. It renders only that version and calls an injected Telegram sender outside the database transaction. Send failures retry only the delivery with a three-attempt default, so they cannot repeat text, transcription, or image generation. Preview delivery is at least once: a process failure or timeout after Telegram accepted a message but before local confirmation can produce a duplicate preview, never duplicate paid generation. Invalid or missing persisted payloads fail closed without a network call.

Text editing uses a durable single-owner input binding. A review callback records the draft, immutable base version, edit mode, and Telegram prompt message before the next response is accepted. Manual text replaces nothing: it creates the next immutable version and an outbox preview without paid work. An AI revision persists the private comment against one budgeted job, and the provider worker loads only that exact base version and comment. A mismatched explicit reply is rejected, a second simultaneous binding is not allowed, and `/new` returns the unchanged draft to review before clearing its binding.

Voice can satisfy an AI-revision binding for either text or image, but not a manual-text or owner-image binding. Dispatch atomically reserves one transcription and its exact generation job; a durable dependency makes the latter ineligible for leasing until the former succeeds. This reserves the combined worst-case cost before the first paid call. The worker validates the persisted binding and local audio before crossing the provider boundary, transcribes once, stores the transcript as the private revision comment, transitions the same draft into generation, and consumes the binding in one transaction. Missing pre-call input fails the transcription and cancels the untouched dependent reservation; an ambiguous transcription outcome cancels the dependent job and keeps the binding locked for manual review.

Image editing uses a separate durable binding that is mutually exclusive with text editing. Revision and upload callbacks name the exact displayed image and its source text version. A revision job is reserved only after the owner sends a bound comment; the worker verifies the prior original stays under the media root and matches its stored checksum before passing it to the injected image provider. Each result becomes a new immutable image version. Returning to text clears approval pointers, preserves prior images, and queues the exact current text for review. Text and image cancel callbacks use distinct action names so their version numbers cannot be confused.

Owner-written text can enter through `/text <post>` as an immutable first text version without a provider job. Text review exposes a separate approve-and-upload action; its durable image binding permits image version zero, so the first owner PNG/JPEG can be stored without an image-generation call. Generated image requests include the exact approved post. Ordinary image feedback edits the checksummed prior image, while explicit concept-reset language deliberately omits the source image and requests a different semantic angle, subject, metaphor, and composition.

A bound owner upload may arrive as a Telegram photo or document. The boundary downloads it with a 10 MB ceiling, derives PNG/JPEG type and dimensions from bounded binary headers rather than trusting Telegram metadata, and atomically moves a `0600` staging file into the draft media directory. The dispatcher records a checksummed immutable image version and exact review outbox entry in the surrounding database transaction without creating a paid job. Normal failures remove the moved file while the transaction rolls back; a process crash between the filesystem move and database commit can leave only an unreferenced orphan for later cleanup, never a database row pointing to missing bytes. Telegram can recompress photos, so owners should send a document when exact original bytes matter.

The Telegram boundary uses the official HTTPS Bot API through a narrow injectable transport. A bounded `getUpdates` iteration accepts only message and callback updates, delegates authorization and deduplication to the existing parser and dispatcher, and advances its in-memory offset only after each handled update. Voice bytes are size-bounded, written through a private temporary file, fsynced, and atomically moved to the deterministic worker path before a transcription job is committed. The real delivery adapter uses `sendMessage` for full text reviews and `sendPhoto` only for Telegram previews; the checksummed original remains the LinkedIn source. Telegram response bodies and token-bearing URLs never appear in raised errors.

`PraecoRuntime` owns the in-memory Telegram offset and runs one bounded poll followed by bounded provider-job and delivery drains. It derives UTC lease, retry, and billing timestamps from one injected clock. Per-tick limits prevent a continuously replenished queue from blocking cooperative shutdown. The continuous loop accepts an event-compatible stop signal; shutdown latency is bounded by the configured Telegram long-poll timeout. Russian command acknowledgements are best-effort and never control durable work, while generated previews remain restart-safe in the delivery outbox.

The executable composition root validates local settings, applies migrations, and owns the SQLite connection, runtime, health listener, and cooperative `SIGINT`/`SIGTERM` event. Publishing defaults to disabled and cannot be enabled without a complete LinkedIn OAuth configuration. Its `--check` path constructs and closes the application without polling Telegram or providers. Recoverable Telegram and SQLite errors make readiness fail while the single process waits and retries; startup and unexpected runtime failures are reported only through sanitized categories.

The HTTP listener serves only `/health/live` and `/health/ready`. It never returns owner identity, credentials, paths, queue contents, drafts, transcripts, or provider inputs. Liveness reflects the process listener; readiness reflects migration completion and the current bounded runtime state. The packaging baseline is described below; an always-on host remains future work.

The Compose baseline runs that single process from a digest-pinned Python image as UID/GID `10001:10001`. The root filesystem is read-only; Linux capabilities are dropped; privilege escalation is disabled; and no port is published to the host. A named volume mounted at `/var/lib/praeco` persists both SQLite state and original media. Only the owner ID and Telegram token are injected from the local environment in mock mode, so dormant OpenAI and LinkedIn credentials are not present in the container. The maintenance CLI creates AES-256-GCM encrypted, manifest-verified SQLite-and-media backups without placing secrets in the archive; an off-site target remains part of the hosting decision.
